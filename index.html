كوكيين منفصلين دلوقتي: auth_token (وصول عادي) وauth_refresh (JWT بعلامة purpose: 'session_refresh'). أي توكن معلّم بـpurpose مرفوض في المسارات العادية، والعكس. إصلاح مصاحب ضروري: بروكسي الـNext.js كان بيستخدم headers.set() لكل هيدر رد، وده بيمسح أي Set-Cookie سابق بنفس الاسم — من غير الإصلاح ده (بقى getSetCookie()/.append())، إضافة الكوكي التاني كانت هتكسر الأول بصمت في production. إصلاح مصاحب تاني: apiFetch بقى يفرّق بين فشل تجديد "أكيد" (401/403 → تسجيل خروج) وفشل "مؤقت" (503/network → تسيب الجلسة، تحاول تاني) — ده بالظبط اللي كان ناقص عشان fail-closed بتاع Redis (503 وقت مفيش worker واحد) ميبقاش بيطرد المستخدم غلط.

ملاحظة صغيرة (مش بند مفتوح): الفصل اتجاه واحد عمليًا — توكن refresh miقدرش يُستخدم كـaccess (مؤكد ومحمي)، لكن access token يقدر يستخدم endpoint التجديد لو اتبعت كـBearer صريح بدل كوكي الـrefresh (الشرط usingRefreshCookie بيبقى false وقتها فيرجع للمسار العادي). راجعنا auth.ts كامل: ده مش privilege escalation (نفس صلاحيات التوكن أصلًا)، وشكله legacy path مقصود لجلسات الطلاب المنتحَلة (توكن حقيقي في localStorage بدل كوكي) — يستاهل تأكيد إن المسار ده لسه مطلوب فعليًا.
